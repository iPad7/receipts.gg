# receipts.gg (가제) — MVP 제품 요구사항 정의서 (PRD)

- **버전:** 0.2
- **개정일:** 2026-10-13
- **상태:** 개발 기준선 초안 (실사용 수요 미검증)
- **관련 문서:** `DOMAIN_MODEL.md`, `AGGREGATE_DESIGN.md`, `IA_USER_FLOW.md`, `WIREFRAMES.md`, `SOFTWARE_ARCHITECTURE.md`

> **명칭 정책:** `receipts.gg`는 제품 **가제**이며, 도메인 등록·소유·배포 사실을 의미하지 않는다. 문서의 `site_id`·`site_slug`는 제품 이름이 아니라 입점 스트리머의 사이트 식별자이다.

## 1. 제품 개요

**제품 정의:** SOOP 개인·소규모 버튜버를 위한 맞춤형 공개 홈페이지 및 방송 운영 도구. 최초에는 개발자가 스트리머별 사이트를 구성·제공하며, 재사용 가능한 코드베이스로 향후 확장할 수 있도록 한다.

**일차 목표:** 취업 포트폴리오로서 요구사항 분석, Python 백엔드 설계, 테스트, 배포 및 운영 능력을 증명한다. **제품 목표:** 실제 스트리머에게 무료 시범 사이트를 제안하고 가능하다면 운영 피드백을 얻는다. 실사용 고객 확보는 기술적 완료의 필수 조건이 아니다.

**초기 범위:** 한 스트리머 사이트, 비로그인 PUBLIC, 인증된 ADMIN, CMS + 수동 RMS. 보상 룰렛을 직접 돌리는 엔진은 제공하지 않는다.

## 2. 사용자와 권한

| 사용자 | 인증 | 가능한 작업 |
|---|---|---|
| PUBLIC | 없음 | 공개 프로필·일정·공지·룰렛 정보·업보 조회 |
| ADMIN | 필수 | 사이트 CMS·룰렛 정의·보상 기록·이행·감사 이력 관리 |

- MVP는 시청자 회원가입·로그인을 지원하지 않는다.
- PUBLIC의 닉네임 검색은 **본인 인증 수단이 아니다**.
- 관리자 권한은 클라이언트 화면뿐 아니라 서버에서 검증한다.
- `site_id`는 데이터 소유·권한 범위이며 제품 브랜드를 의미하지 않는다.

## 3. 공개 근거 및 가설

공개 SOOP 방송국, 링크 허브, 업보 장부 등에서 프로필·일정·룰렛 확률 안내·업보 조회·방셀 옵션 신청·보상 이행 공지가 실제 형태로 존재함을 확인했다. 이것은 **기능 존재의 근거**이지 스트리머가 현재 도구를 불편해한다거나 신규 서비스에 지불 의사가 있다는 증명은 아니다.

- H-001: 독립 홈페이지·운영 관리 통합은 일부 스트리머에게 유용할 수 있다.
- H-002: 보상 획득 이력과 보상 이행 관리 분리가 누락 방지에 도움이 될 수 있다.
- H-003: 무료 맞춤 제작 제안으로 시범 사용자를 확보할 수 있다.

## 4. MVP 기능 요구사항 (P0)

### FR-001 — 공개 홈페이지

**설명:** 스트리머 프로필, 소개, SOOP·SNS 링크, 방송 일정 요약, 최근 공지, 룰렛·업보 진입점 제공.

**수용 기준**
- AC-001-1: 비로그인 상태로 공개 페이지에 접근할 수 있다.
- AC-001-2: 공개로 설정한 콘텐츠만 반환한다.
- AC-001-3: 모바일·데스크톱 주요 화면에서 가로 넘침 없이 탐색 가능하다.
- AC-001-4: 숨김 콘텐츠에 직접 URL로 접근해도 공개되지 않는다.

### FR-002 — 관리자 CMS

**설명:** 프로필, 대표 이미지, 링크, 일정, 공지를 코드 수정 없이 변경한다. 프로필·링크·일정은 저장 시 반영, 공지는 임시저장/게시 상태를 구분한다.

**수용 기준**
- AC-002-1: ADMIN의 수정·게시가 공개 화면에 반영된다.
- AC-002-2: 잘못된 입력·비허용 URL은 검증 오류로 거부된다.
- AC-002-3: 비로그인 사용자는 CMS 변경 API에 접근할 수 없다.
- AC-002-4: 비게시 공지는 PUBLIC API와 직접 링크에서 제외된다.

### FR-003 — 룰렛 정의·보상 안내

**설명:** 룰렛 이름, 설명, 보상 종류, 수동 입력 확률(선택), 공개 여부를 관리한다. 실제 추첨·후원 처리는 하지 않는다.

**수용 기준**
- AC-003-1: 공개 룰렛만 PUBLIC에 나타난다.
- AC-003-2: 확률은 유효 범위로 검증하며 미입력 값을 임의로 표시하지 않는다.
- AC-003-3: 수동 입력 정보임을 명시한다.
- AC-003-4: 보상 정의를 수정·비활성화해도 기존 지급 보상 스냅샷은 유지된다.

### FR-004 — 보상 획득 기록

**설명:** 관리자는 룰렛 당첨, 직접 지급 등 보상 획득 사건을 기록한다. 사건(`RewardAcquisitionEvent`) 1건에서 보상 권리(`RewardGrant`) N개(최소 1개)를 생성한다. 보상 1단위는 개별 Grant로 관리한다.

**사건 유형:** `ROULETTE_DRAW`, `MANUAL_AWARD`, `LEGACY_IMPORT`.
**입력·기록 출처:** `MANUAL`, `CSV_IMPORT`, `INTEGRATION`.

MVP에서는 수동 등록만 실제 구현한다. `LEGACY_IMPORT`라는 개념은 모델에서 수용하되 CSV 일괄 가져오기는 P1이다. 발생 시각을 모르면 `occurred_at`은 미상으로 보존하고 `recorded_at`만 기록한다.

**수용 기준**
- AC-004-1: 단일 사건에서 복수 보상 항목·수량을 등록할 수 있다.
- AC-004-2: 방셀 3장은 각각 독립적으로 처리 가능한 Grant 3개로 등록된다.
- AC-004-3: 사건·Grant·필요한 Fulfillment·감사 로그는 원자적으로 저장된다.
- AC-004-4: 동일 요청 키 재시도로 중복 등록되지 않으며 같은 키의 다른 본문은 충돌 처리된다.
- AC-004-5: 관리 작업자와 기록 시각을 추적할 수 있다.

### FR-005 — 보상 이행 및 권리 정정

**설명:** 이행이 필요한 Grant에는 `Fulfillment`가 하나 연결된다. 이행 상태는 `PENDING`, `IN_PROGRESS`, `FULFILLED`이고, 오기록 권리를 무효화할 경우에만 `CANCELLED`가 연동된다.

**권리 상태:** `RewardGrant.ACTIVE` / `RewardGrant.VOIDED`.

**수용 기준**
- AC-005-1: 유효한 Grant의 이행 상태를 독립적으로 변경할 수 있다.
- AC-005-2: 완료 처리 시 완료 시각을 기록한다.
- AC-005-3: 완료 정정 시 이유를 요구하고 이전 상태를 감사 로그에 보존한다.
- AC-005-4: 정상적인 보상 지연을 `CANCELLED`로 처리할 수 없다.
- AC-005-5: 미완료 오기록의 무효화는 `ACTIVE → VOIDED`와 **존재하는 Fulfillment의** `→ CANCELLED`를 동일 트랜잭션으로 처리하고 사유를 남긴다. 이행 불필요 보상은 Fulfillment 없이 Grant만 무효화한다.
- AC-005-6: 이미 완료된 보상은 완료 기록을 명시적으로 정정하기 전에 바로 무효화할 수 없다.
- AC-005-7: 오래된 버전의 상태 변경은 충돌로 거부된다.

### FR-006 — 공개 업보 장부

**설명:** 비로그인 방문자는 관리자가 명시적으로 공개한 보상과 이행 정보를 검색·필터할 수 있다. 개별 Grant는 **기본 비공개**이다.

**수용 기준**
- AC-006-1: 별도 로그인 없이 공개된 업보만 조회할 수 있다.
- AC-006-2: 비공개 보상 존재 여부와 관리 메모·내부 식별자가 응답에서 누출되지 않는다.
- AC-006-3: 검색 및 필터 결과·공개 집계가 일치한다.
- AC-006-4: 즉시 지급되어 Fulfillment가 없는 보상은 미이행 집계에 들어가지 않는다.
- AC-006-5: 닉네임 검색 화면에서 계정 본인 인증으로 오해하지 않게 안내한다.
- AC-006-6: 서버 저장 후 마지막 갱신 정보를 확인할 수 있다.

### FR-007 — 관리자 인증·인가

**설명:** 관리자 전용 서버 세션 로그인, 로그아웃, 사이트별 권한 검증.

**수용 기준**
- AC-007-1: 미인증 변경 요청은 거부된다.
- AC-007-2: 인증된 계정도 허용된 사이트의 데이터만 관리할 수 있다.
- AC-007-3: 로그아웃·세션 만료 이후 재사용은 거부된다.
- AC-007-4: 쿠키 인증 기반의 변경 요청에 CSRF 보호를 적용한다.

### FR-008 — 감사 기록

**설명:** 보상 생성·완료·정정·무효화 등 주요 관리자 변경 기록을 보존한다.

**수용 기준**
- AC-008-1: 작업자·대상·시각·전후 상태·사유(필요 시)를 조회할 수 있다.
- AC-008-2: 감사 기록은 주요 데이터 변경과 함께 성공·실패한다.
- AC-008-3: PUBLIC은 감사 기록을 조회할 수 없고 ADMIN UI에서 이를 임의로 변경할 수 없다.

### FR-009 — 관리자 대시보드

**설명:** 전체 유효 보상, 이행 대기, 이행 중, 완료, 이행 불필요 등 **상호 구별되는 지표**를 표시하고 업보 등록·관리 화면으로 연결한다.

**수용 기준**
- AC-009-1: `ACTIVE` Grant를 기준으로 유효 보상을 집계한다.
- AC-009-2: 미이행 = `ACTIVE` Grant의 Fulfillment가 `PENDING` 또는 `IN_PROGRESS`인 수량이다.
- AC-009-3: 완료 = `ACTIVE` Grant의 Fulfillment가 `FULFILLED`인 수량이다.
- AC-009-4: Fulfillment가 없는 즉시 지급 보상은 '이행 불필요'로 별도 집계한다.
- AC-009-5: 상세 목록과 대시보드 수치가 일치한다.

## 7. 대표 인수 시나리오

1. 관리자가 보상 3개 등록 → 사건 1건/Grant 3개/이행 작업 3개 생성.
2. 한 개만 완료 → 완료 1개, 미이행 2개.
3. 같은 멱등성 키로 같은 요청 재전송 → 추가 생성 0건.
4. 같은 키로 다른 본문 → 충돌.
5. 완료 상태를 사유와 함께 IN_PROGRESS로 정정 → 이전 완료 이력 보존.
6. 잘못 등록된 미완료 Grant 무효화 → 권리 VOIDED, 이행 CANCELLED, 감사 로그.
7. PUBLIC 업보 검색 → 개별 공개 허용된 데이터만 표시.
8. 즉시 지급 보상 생성 → Fulfillment 없음, 미이행 수량 불변.
9. 미인증/다른 사이트 관리자 요청 → 권한 오류.
10. 두 ADMIN이 같은 보상 버전으로 변경 → 하나가 성공하면 나머지는 충돌.

## 8. 출시 기준과 검증 한계

- [ ] 가상 스트리머 공개 사이트 URL이 배포된다.
- [ ] ADMIN은 CMS·룰렛·수동 RMS·감사 로그를 사용할 수 있다.
- [ ] 핵심 도메인 규칙과 보안·정합성 테스트가 통과한다.
- [ ] 설치·실행·배포·복구 방법이 문서화된다.
- [ ] 데모 데이터는 가상임을 명시한다.

실사용 고객의 요구와 가치 판단은 시범 운영 전까지 **가설**이다. `receipts.gg`의 도메인 소유 및 실제 배포 여부도 별도 확인 사항이다.
