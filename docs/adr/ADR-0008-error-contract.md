# receipts.gg (가제) — ADR-0008 — 오류 응답 계약과 도메인 예외 변환

- 날짜: 2026-10-13
- 상태: Proposed
- 참조: SOFTWARE_ARCHITECTURE.md §5·§7·§8·§12, AGGREGATE_DESIGN.md, ADR-0003·ADR-0005, DEVELOPMENT_PLAN.md BE-01/BE-05, FE-00

## 맥락

SA §7 은 상태 코드만 규정한다. 그런데 이 제품에서 **409 Conflict 는 최소 네 가지 서로 다른 사건**을 의미하고, 각 사건에서 프론트엔드가 해야 할 복구 동작이 모두 다르다.

| 사건 | 근거 | 필요한 복구 동작 |
|---|---|---|
| 같은 멱등성 키 + 다른 요청 본문 | SA §6.4 | 새 키로 재요청 |
| 두 관리자의 동시 수정(버전 충돌) | SA §6.5 | 최신 데이터 재조회 후 재시도 |
| 완료된 보상을 직접 무효화 시도 | PLAN BE-05 | 완료 기록 정정 절차로 유도 |
| 이행 불필요 Grant 의 이행 상태 변경 | SA §6.3 | 재시도 불가 안내 |

`{"detail": "Conflict"}` 로는 이 분기가 불가능하다. FE-00 의 "Conflict UI 공통화" 요구를 충족할 수 없고, 사람이 읽는 메시지 문자열로 분기하면 문구를 고치는 순간 프론트엔드가 깨진다.

## 결정

**1. 응답 형식.** RFC 9457 Problem Details(`application/problem+json`)를 사용한다. 안정적인 기계 식별자 `code` 를 포함하고, `type` 은 `code` 에서 URN 으로 기계적으로 파생한다(URL 호스팅 불필요, 이중 관리 없음). `title`·`detail` 은 사람이 읽는 문구이므로 계약에 포함하지 않으며 언제든 변경할 수 있다. FastAPI 기본 응답과 Pydantic 의 422 형식도 예외 핸들러로 같은 형식으로 통일한다.

**2. 코드 명명.** `<모듈>.<사유>` 소문자 점 표기를 쓴다(예: `rms.grant_version_conflict`). 모듈 접두사가 SA §4 의 모듈 경계를 반영해 이름 충돌을 막고, 영향 범위를 검색할 수 있다.

**3. 계층 책임.** 도메인 예외는 HTTP 를 모른다. 도메인 예외는 안정적인 `code` 만 보유하고, **상태 코드 매핑은 Presentation 계층의 단일 중앙 테이블**에 둔다. `DomainError` 의 모든 하위 클래스가 그 테이블에 존재하는지 검사하는 테스트를 둔다. 이 테스트가 없으면 새 예외를 추가하고 매핑을 잊는 순간 그 예외가 500 과 스택트레이스로 새어 나간다.

**4. 상태 전이 위반은 409.** 스키마·형식 오류는 422(Pydantic 자동), 불변식·상태 전이 위반은 409 로 응답한다. 422 는 "입력 형식이 처리 불가"이고 이 경우는 "현재 리소스 상태와 요청이 충돌"이므로 409 가 의미적으로 정확하다.

**5. 권한 없는 리소스는 404.** 인증된 관리자의 허용 사이트를 벗어난 리소스나 비공개 리소스는 403 이 아니라 404 로 응답해 **존재 여부를 숨긴다**(ADR-0005 의 사이트 격리, SA §8 의 기본 비공개). 403 은 동작 자체가 금지된 경우(CSRF·Origin 검증 실패 등)에 사용한다.

**6. 카탈로그 관리.** 오류 코드 목록은 **코드의 Enum 이 유일한 소스**다. 이 ADR 과 다른 문서에 목록을 복제하지 않는다. OpenAPI `responses` 에 반영하고, 실제 응답과 OpenAPI 의 일치는 테스트로 확인한다(BE-07 게이트 항목).

**7. 정보 노출.** Public 응답에는 진단용 확장 필드를 포함하지 않는다. 내부 SQL·DSN·세션 식별자·스택트레이스·비공개 메모는 어떤 응답에도 넣지 않는다(SA §8·§12). 응답에 `request_id` 를 포함해 사용자 신고와 서버 로그를 연결한다.

**8. 구현 시점.** BE-01 에서 공통 골격과 `common.*` 코드만 만든다. 도메인별 코드는 해당 규칙이 실제로 구현되는 단계(BE-02 인증, BE-05 RMS)에서 추가한다. 구현 전에 카탈로그를 열거하지 않는다.

멱등성 성공 재생(같은 키 + 같은 본문)은 오류가 아니라 기존 결과를 정상 응답으로 반환하므로 이 계약의 범위 밖이다.

## 검토한 대안

- **FastAPI 기본 `{"detail": "..."}`:** 문자열이라 기계 판독이 불가능하고, 문구 변경이 곧 계약 파기다.
- **커스텀 envelope(`{"error": {...}}`):** 동작은 동일하지만 비표준이라 설명 비용이 든다. RFC 9457 과의 실질 차이는 필드명뿐이고, 어차피 FastAPI 기본·422 형식을 통일해야 하므로 표준을 택하는 추가 비용이 사실상 없다.
- **숫자 코드(`RMS-1001`):** 문서를 봐야 의미를 알 수 있고 코드에서 검색하기 어렵다.
- **예외 클래스에 `status_code` 속성:** 구현은 간단하지만 도메인이 HTTP 를 알게 되어 SA §5 의 계층 분리가 깨지고, 전체 오류 계약을 한곳에서 볼 수 없어 누락 검사 테스트가 불가능하다.
- **권한 없는 리소스에 403:** Admin UX 는 명확해지지만 "그 리소스가 존재한다"는 사실이 누출된다.

## 결과와 트레이드오프

프론트엔드가 `code` 로 안정적으로 분기할 수 있고, 메시지 문구를 자유롭게 바꿀 수 있다. 대신 다음을 받아들인다.

- 예외 핸들러를 직접 작성해 FastAPI 기본·Pydantic 422 형식을 통일해야 한다.
- 404 숨김 정책은 관리자에게 "권한이 없는지 없는 리소스인지" 모호하게 보일 수 있다. 안내 문구로 보완한다.
- `request_id` 는 요청 ID 미들웨어가 선행되어야 한다(SA §12). 미들웨어가 없으면 해당 필드는 생략한다.

## 재검토 조건

외부 파트너에게 API 를 공개할 때, 다국어 오류 메시지가 요구될 때, 또는 전송 방식이 REST 외로 확장될 때 재평가한다.
