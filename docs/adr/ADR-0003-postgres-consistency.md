# receipts.gg (가제) — ADR-0003 — PostgreSQL 트랜잭션 및 동시성 정책

- 개정:
  - 2026-10-16 — 트랜잭션 경계 구현 방식 보강 (BE-01 3단계)
  - 2026-10-13 / 문서 패키지 v0.3 (참조 절 보정, 외부 이벤트 키 컬럼명 보정, 제품 가제 변경)
- 날짜: 2026-10-13
- 상태: Proposed
- 참조: AGGREGATE_DESIGN.md, SOFTWARE_ARCHITECTURE.md §6·§7·§11, ADR-0007, ADR-0009

## 맥락
한 사건이 여러 RewardGrant/Fulfillment를 생성한다. 네트워크 재시도, 동시 관리자 수정, 잘못된 취소는 보상 장부의 신뢰성을 훼손할 수 있다.

## 결정
PostgreSQL 트랜잭션으로 사건·보상·이행 작업·감사 기록·멱등성 결과를 원자적으로 저장한다. `(site_id, idempotency_key)`를 유일성 제약으로 보호하고 동일 키의 다른 요청 본문은 충돌 처리한다. 외부 이벤트에는 `(site_id, external_system, external_event_id)` 고유성을 적용한다(외부 ID가 존재하는 경우). RewardGrant에 낙관적 버전을 둔 뒤, 자식 Fulfillment 변경 시에도 루트 버전을 증가시킨다. 즉시 지급 보상처럼 Fulfillment가 없는 ACTIVE Grant도 별도로 집계하며, 정상적인 지연을 CANCELLED로 처리하지 않는다.

## 검토한 대안
- 애플리케이션 메모리에서 중복 판정: 동시 요청과 재시작에 안전하지 않다.
- 비동기 이벤트별 후속 쓰기: 부분 성공 및 복구 절차가 복잡하다.
- 무조건 마지막 수정 덮어쓰기: 운영자의 수정 손실이 생긴다.

## 결과와 트레이드오프
쓰기 트랜잭션 범위가 명확해지지만 잠금·충돌 재시도 처리 및 실제 PostgreSQL 기반 통합 테스트가 필요하다. ORM의 버전 검사 기능만으로 자식 엔티티 변경을 자동으로 보호한다고 가정하지 않는다.

## 재검토 조건
고부하, 다중 DB, 비동기 대량 수집이 도입되면 처리 모델을 재평가한다.

## 보강: 트랜잭션 경계의 구현 방식 (2026-10-16, BE-01 3단계)

### 맥락

위 결정은 "원자적으로 저장한다"는 요구를 정했지만 **경계를 코드의 어디에 두는지**는 정하지 않았다. BE-01에서 "요청 1건 = 트랜잭션 1건"을 FastAPI의 `yield` 의존성 종료 시점에 커밋하는 방식으로 구현하려 했으나, 실측으로 그 방식이 성립하지 않음을 확인했다.

### 실측 결과

`DEFERRABLE INITIALLY DEFERRED` 제약으로 **커밋 시점에만** 실패하는 상황을 만들어 확인했다.

```text
라우트 정상 반환 → 응답 본문 직렬화 → 의존성이 commit() → IntegrityError
클라이언트가 받은 응답: 200
실제 DB 상태: 롤백 (저장되지 않음)
```

의존성 종료 코드의 실행 순서도 관찰했다: `['route.body.built', 'dependency.commit']`. 커밋이 응답 본문 생성 **뒤**에 실행되므로 그 시점에는 상태 코드를 바꿀 수 없다.

즉 의존성에서 커밋하면 **"저장되지 않았는데 성공 응답"**이 가능하다. 우리 스키마의 제약은 전부 즉시(NOT DEFERRABLE)라 대부분의 위반은 문장 시점에 드러나지만, 커넥션 손실·직렬화 실패는 커밋 시점에 발생한다. 범위는 좁고 실패는 조용하다 — 장부 제품에서 가장 나쁜 조합이다.

### 결정

**커밋은 라우트 호출 경로 안에서 수행한다.**

- 세션 의존성(`api/dependencies.get_session`)은 세션 제공과 정리만 책임진다. **커밋하지 않는다.** 예외 시 롤백하고, 커밋되지 않은 트랜잭션이 남아 있으면 롤백한다.
- 쓰기 유스케이스는 `core.transaction.transactional(session)` 블록 안에서 수행한다. 블록이 정상 종료하면 커밋하고, 예외가 나면 롤백한 뒤 다시 던진다.
- 읽기 전용 경로에는 이 블록을 쓰지 않는다.

TX-001~004의 "이 범위가 한 트랜잭션"이라는 서술이 코드에서 블록으로 드러난다.

### 검토한 대안

- **의존성 종료 시 커밋:** 유스케이스가 커밋을 신경 쓰지 않아도 되지만, 위 실측대로 커밋 실패를 보고할 수 없다.
- **라우트/서비스가 직접 `session.commit()`:** 실패 보고는 해결되지만 커밋을 잊으면 "200 + 미저장"이 되고, 트랜잭션 경계가 코드에서 흩어진다.
- **미들웨어에서 커밋:** 응답 직전에 커밋해 상태 코드를 바꿀 수 있으나, 미들웨어가 DB와 오류 응답 생성을 모두 알아야 해 결합이 커진다.
- **Repository/Unit of Work 추상화:** ADR-0009에서 기각했다. `transactional`은 `Session`을 감싸거나 숨기지 않고 트랜잭션 범위에 이름만 붙인다.

### 결과와 트레이드오프

커밋 실패가 요청-응답 주기에서 보고되고, 경계가 코드에 명시된다. 남는 실패 모드는 **`transactional` 블록을 아예 쓰지 않은 쓰기**이며, 이 경우 데이터는 조용히 저장되지 않는다(롤백). 조용한 저장보다는 안전하지만 여전히 버그이므로, 각 쓰기 유스케이스의 영속 여부를 통합 테스트가 단정해야 한다.
