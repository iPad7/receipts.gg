# receipts.gg (가제) — ADR-0007 — 동기 SQLAlchemy + psycopg3 채택

- 날짜: 2026-10-13
- 상태: Proposed
- 참조: SOFTWARE_ARCHITECTURE.md §1·§5·§6, ADR-0003, DEVELOPMENT_PLAN.md BE-00/BE-05

## 맥락

DB 접근을 동기로 할지 비동기로 할지 결정해야 한다. 이 선택은 BE-01 의 세션·트랜잭션 경계와 BE-05 의 테스트 전략 전체에 영향을 준다.

워크로드 특성:

- 쓰기 경로는 관리자 1~2 명의 수동 입력이다. 동시성이 거의 발생하지 않으며, BE-05 의 낙관적 충돌 테스트는 인위적으로 동시 요청을 만들어야 한다.
- 읽기 경로는 소규모 개인 버튜버의 공개 홈페이지다. 피크를 동시 수십~수백 요청으로 가정해도 평균 동시 실행 쿼리는 한 자릿수다.
- SA §11 의 성능 목표(1만 건, p95 500ms)는 인덱스·쿼리 설계로 결정되며 이벤트 루프와 무관하다.
- 우선순위 1위는 데이터 정합성이다(SA §1).

개발자는 비동기 처리와 락에 대한 이론·실무 경험을 보유하고 있다. 따라서 이 결정은 역량이 아니라 **워크로드 적합성과 유지 비용**의 문제다.

## 결정

동기 SQLAlchemy 2.x + psycopg3 를 사용한다.

- FastAPI 라우터는 `def` 로 통일한다. `async def` 핸들러에서 동기 DB 호출을 하는 혼합은 금지한다(이벤트 루프 블로킹).
- 드라이버는 asyncpg 가 아니라 **psycopg3** 로 고정한다. psycopg3 는 동기·비동기를 같은 드라이버로 지원하므로, 나중에 전환해도 DSN·타입 어댑터·드라이버를 교체할 필요가 없다.
- DB 접근은 Application Service 경계 안에 둔다(SA §5). 라우터가 세션을 직접 다루지 않으므로, 전환 시 수정 범위가 Application/Infrastructure 계층으로 한정된다.
- 커넥션 풀은 `pool_pre_ping` 을 켜고 `connect_timeout` 을 설정한다. 풀 크기는 설정으로 노출해 동기 핸들러가 소비하는 스레드 수와 함께 조정한다.
- 외부 HTTP 호출이나 스트리밍 응답이 필요한 라우터가 생기면 **그 라우터만** 비동기로 두고 DB 에 접근하지 않는다.

## 검토한 대안

- **비동기 SQLAlchemy(AsyncSession):** I/O 동시성 이득이 이 워크로드에 없는 반면 비용은 분명하다. 암묵적 lazy loading 이 불가해 `RewardGrant → Fulfillment` 순회 경로마다 eager loading 을 빠짐없이 지정해야 하고, 누락은 특정 경로에서만 드러난다. BE-02 의 비밀번호 해시 같은 CPU 바운드 작업이 이벤트 루프를 블로킹할 위험이 있다. BE-05 의 롤백·동시 재시도 테스트에 async 픽스처와 이벤트 루프 스코프 문제가 추가 변수로 붙는다. Alembic 도 `run_sync` 래퍼가 필요하다.
- **asyncpg:** 동기 경로가 없어 전환이나 혼합 운용 시 드라이버 교체가 강제된다.
- **동기/비동기 혼합(같은 라우터 안에서):** 이벤트 루프 블로킹을 코드 리뷰로만 막아야 하므로 사고 위험이 크다.

## 결과와 트레이드오프

트랜잭션 경계와 실패 경로의 추론이 단순해지고, 정합성 테스트 작성 비용이 낮아진다. 대신 다음을 받아들인다.

- 동기 핸들러는 anyio 스레드풀을 소비한다. 스레드 수와 커넥션 풀 크기를 정렬해야 하며, 모르면 부하 시 원인 불명의 대기가 발생한다.
- SSE·토큰 스트리밍 응답은 비동기가 명확히 유리하므로, 그런 기능은 별도 경로로 다룬다.
- 전환 시 모든 DB 호출부와 테스트를 수정해야 한다. 양은 있으나 기계적이며, 위의 경계 설계로 범위가 한정된다.

## 재검토 조건

SSE·스트리밍 응답이 제품 요구가 될 때(PRD P3 의 실시간 증거/STT/LLM 포함), 요청 처리 중 외부 API 대기가 상시화될 때, 또는 **측정된** 동시성 한계에 도달할 때 재평가한다. 추정이 아니라 측정 결과를 근거로 한다.
